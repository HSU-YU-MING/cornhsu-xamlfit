# M6 — 全面重讀

把整個專案從頭讀一遍、換角度檢視之後做的事。這一份取代先前文件裡所有的可解析率數字。

**一句話的結論**：先前的引擎在好幾個地方把「不知道」當成「預設值」，於是報出很高、但站不住的可解析率。
補掉之後，自家專案仍在 76~100%，公開的應用程式是 21~33%，控制項庫接近 0 —— 而這次每一個數字都對照過真的 WPF。

之後又做了一件先前做不到的事：把**真實專案的視窗**（帶它自己的佈景與各語言字串）交給真的 WPF 畫出來，跟工具的判斷逐筆對（第 2.6 節、第 4 節）。這一步又找到 11 個問題。

---

## 1. 這一輪是怎麼找到問題的

三個工具，各自抓到別的方法抓不到的東西：

| 方法 | 抓到什麼 |
|---|---|
| 逐檔重讀 | 「讀不出來的值被當成沒設定」這一整類；樣式索引是扁平的；`--culture` 把中性語言濾掉；死掉的設定鍵 |
| **`prototype/LayoutOracle`**：同一段 XAML 同時給真的 WPF 視窗與解析器算 | 視窗邊框、明寫的 Width 也會被外層裁、水平 StackPanel 分寬度、Auto 欄與 StackPanel 裡換行失效、預設字型跟著語言走、`ScrollBar` 的 MinWidth |
| **來源語言自我檢驗**：出貨 App 上寫死的文字理應裝得下，工具報溢出就是工具錯 | `xml:space="preserve"` 沒繼承、UserControl 的字型來自宿主視窗、向量路徑資料被當成文字 |

第一種方法找得到「邏輯上不對」的東西，找不到「我對 WPF 的理解本身是錯的」。
後兩種的對照都不是這支工具自己，所以抓得到。**`ScrollBar Width="10"` 實際是 16.8 寬**這件事，
是在我已經寫好程式碼與單元測試（兩者都照我的錯誤理解通過）之後，由對照程式指出來的。

## 2. 修掉的問題

範本被換掉之後不是只能放棄：**範本就在專案裡**。現在的做法是把範本複製出來、外面套一個已知寬度的框，

### 卡住的原因（各專案最大的幾項）

- **QuillNest**：同一行有好幾個 `Run`（32）、專案重設了 DataGrid 欄標題的樣式（14）、
  寬度取決於其他欄的欄標題（6）、有跨欄子元素的 Auto 欄（3）
- **Playnite**：自訂面板 `GridEx`（99，工具沒見過；它用 `ColumnCount`／`StarColumns` 這些屬性定欄、
  不是 ColumnDefinitions，所以連 `treatAs` 都不適用）、同一排的鄰居寬度不明（55）、
  重寫過的 ScrollViewer 裡的捲軸沒有明寫寬度（19）
- **Kindling**：同一排的鄰居寬度不明（15）
- **ScreenToGif**：收成 `Width="0"` 的面板（318，展開的寬度在動畫裡）
- **MahApps／MaterialDesign／HandyControl／wpfui**：控制項的範本把 Padding、BorderThickness 綁到附加屬性或動態資源；
  示範程式的字型來自標記延伸。這些 repo 裡控制項本身就是佈景

## 4. 先前「還不知道」的事，去確認的結果

| 事項 | 結果 | 怎麼確認的 |
|---|---|---|
| **公開語料上報出來的溢出是不是真的** | **大致是。** Playnite 75 筆全部對照過：71 筆真的被裁，4 筆誤報（2 筆差不到 0.5 px；另外 2 筆是 `ToolsConfigWindow.xaml:52` 同一顆按鈕，偏保守 0.7 與 7.7 px）。**漏報 0。** 工具量的文字寬度比 WPF 寬 −0.02 ~ +1.74 px；可用寬度最多多算 0.02 px | `prototype/CorpusRender` |
| ScreenToGif 的寬度差 | 來自字型，不是版面：這台是繁中 Windows（預設字型正黑體 UI），工具假設的是法文／希臘文／烏克蘭文 Windows（Segoe UI）。給工具同一支字型後：希臘文 932.74 vs 932.72、烏克蘭文 828.67 vs 828.65（#58 修正前是 815.05）、法文的可用寬度 192.74 vs 194.34（偏保守） | 同上，加設定檔 `defaultFontByCulture` |
| **視窗邊框在 100% 縮放的確切數值** | 標準視窗 16 DIP（125% 時 14.4、150% 時 14.67、200% 時 13）；`WindowStyle="ThreeDBorderWindow"` 20；`WindowStyle="None"` 可縮放 14。垂直捲軸 17.00／16.80／17.33／17.14／17.00 DIP。**表裡的 16／20／17.5 正好是各縮放比例下的最大值** —— 方向保守，而且不再是猜的 | `prototype/DpiProbe`（`AdjustWindowRectExForDpi`、`GetSystemMetricsForDpi`） |
| **日文、韓文、簡中系統的預設字型** | WPF 的預設字型就是 `SystemFonts.MessageFontFamily`：在這台確認了（繁中 → 正黑體 UI）。日韓簡中**沒有在那些系統上量** —— 要改這台的 Windows 顯示語言，那是你的決定，我沒有動。另外確認：**缺字的後備跟 Windows 的語言無關**，看的是元素的 Language（#53） | LayoutOracle `--font-source`、`--fallback` |
| **Linux 上的實際執行** | 還是沒跑到：這台沒有 WSL（只有安裝用的 stub）也沒有 Docker。做得到的都做了：`linux-x64` 發佈只相依 `Microsoft.NETCore.App`、產出 ELF 啟動檔；在 Windows 上開 `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1`（Linux CI 映像檔常見的設定）跑全部測試與兩個語料的完整檢查 —— 結果跟一般模式逐筆相同。這個模式抓到 #54 | invariant 模式重跑 |
| **release workflow 與 composite action** | 本機照 workflow 的步驟彩排：建置、測試、三支驗證腳本、打包、從本機 nupkg 安裝、`--version`、實際執行，都通過。Action 腳本的 5 個情境退出碼是 1／0／1／2／2，符合預期；參數注入的測試沒有建出任何檔案。**跑不到的**：從 nuget.org 安裝、Trusted Publishing 的登入與推送、GitHub 代管的 runner | `scratchpad/release-rehearsal` |
| **資源字典是不是真的被合併進應用程式** | 對 Playnite 與 ScreenToGif 成立：CorpusRender 用專案自己的 `App.xaml` 去載（Playnite 87 個字典載得進 86 個），結果跟工具一致。一般情況仍是假設 | CorpusRender |
| **字型授權** | 查過：Microsoft 的字型 FAQ 禁止再散布與轉換字型，**沒有提到萃取度量**。美國著作權局 1988 年的立場（據 Richard Kinch 的整理）是字型度量不受著作權保護；市面上也有度量相容的字型（Liberation 等）。**沒有定論，這不是法律意見** —— 工具照舊不附任何專有字型的度量，發版前請律師確認仍是待辦 | 網路查證 |

### 還是不知道的事

- **Linux 實機、GitHub 代管的 runner、nuget.org、Trusted Publishing**：要嘛把 repo 推到 GitHub（私人的也可以）讓 CI 跑，
  要嘛在這台裝 WSL。兩個都要你決定。
- **日文、韓文、簡中 Windows 的預設字型**：要在那些系統上量。
- **字型度量的授權**：要律師。
- **CorpusRender 畫不出來的東西**：下拉選單的內容、資料範本裡的文字、隱藏的面板。那些位置的判斷沒有對照過。
- **樣本仍然小**：兩個專案、14 個視窗。
