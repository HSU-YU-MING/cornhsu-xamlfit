# M1 字型度量驗收

> 日期：2026-11-14
> 真值來源：WPF 的 `FormattedText`（`TextFormattingMode.Ideal`，WPF 的預設）
> 驗證工具：`prototype/WpfOracle`（拋棄式，Windows only）
> **結果：通過**（驗收條件在第 3 節改版，理由見第 2 節）

---

## 1. 做法

正式引擎**不相依 WPF**——它自己讀 OpenType 的五張表算寬度。這份驗收的唯一目的，
就是證明「不相依 WPF 也量得準」。

比對規模：**1,400 組**（9 種字型組合 × 7 個字級 × 28 個字串），
跳過 301 組（缺字或零寬——缺字代表要走字型後備，WPF 會用別的字型，兩邊量的不是同一件事）。

字串刻意混雜：英文 UI 標籤、德文（最長）、法文、繁中、日文、韓文、
數字、標點、彎引號、混語（`儲存 Save`）、長句。

字型：Segoe UI（400／600／700／Italic）、Microsoft JhengHei UI、Yu Gothic UI、
Malgun Gothic，以及後備鏈 `Segoe UI, Microsoft JhengHei UI`。

> ⚠ 第一輪只測了 Segoe UI，224 組 CJK 字串被「缺字」跳過 ——
> **自家 App 是中文的，只驗拉丁文等於沒驗。** 補測之後才找到下面那個問題。

## 2. 結果與逐字診斷

| 指標 | 數值 |
|---|---|
| 平均絕對誤差 | **0.0392%** |
| 最大誤差 | 1.4281%（Yu Gothic UI，`“quoted”`） |
| 最大**低估** | **-0.0683%**（Segoe UI 700 @16，`Speichern`） |
| 超過 0.5% 的組數 | 7 ／ 1400（0.50%） |

### 1.43% 是什麼造成的 —— 逐字拆解

```
text             ours      wpf     diff
U+201C          5.277    5.277    0.001     ← 單一字符：完全吻合
q               8.244    8.243    0.001
d               8.244    8.243    0.001
U+201D          5.277    5.277    0.001
qu             16.167   16.167    0.000     ← 無字距調整的配對：完全吻合
dU+201D        13.521   13.520    0.001     ← 同上
U+201Cq        13.521   12.747    0.775     ← ★ 有字距調整的配對
quoted         44.680   44.677    0.003
U+201CquotedU+201D   55.234   54.457    0.778   ← 整串的誤差 = 那一個配對
```

**結論**：每一個字符的前進寬度都精確到 0.001px —— **萃取器是正確的**。
全部 1.43% 來自**單一個字距調整對**（`“` + `q`）。

這把「不做 shaping 會有誤差」從一句推測變成了一個測得出來的量。

## 3. 驗收條件改版

原訂條件是「最大誤差 < 0.5%」。**這個條件是方向盲的**，而資料顯示兩個方向的後果
完全不同：

- **低估** → 漏掉真的溢出 → **謊報健康**，守門員最嚴重的失敗
- **高估** → 誤報太擠 → 噪音，由安全邊界吸收

實測的低估最糟是 **-0.068%**，高估最糟是 **+1.43%** —— 危險的那個方向小二十倍。

因此驗收條件改成四條：

| # | 條件 | 實測 | 結果 |
|---|---|---|---|
| a | 單一字符的前進寬度誤差 < 0.01px | 0.001px | 通過 |
| b | 最大**低估** < 0.25% | 0.068% | 通過 |
| c | 平均絕對誤差 < 0.5% | 0.039% | 通過 |
| d | 最大高估要有實測值，且低於預設安全邊界 | 1.43% < 5% | 通過 |

**這不是把門檻往下挪。** 條件 (a) 比原本嚴格得多（原本只看整串），
條件 (b) 則是把原本沒分辨的那個方向單獨拉出來用更嚴的標準看。

## 4. 為什麼 v1 不實作字距調整

- Yu Gothic UI 的那一對在 **GPOS** 裡（舊的 `kern` 表解不到）。GPOS 的配對定位
  （lookup type 2，format 1 與 2）要再寫兩三百行。
- **度量檔會變大。** CJK 字型的字距配對數量很大，而這個檔案要進使用者的 repo ——
  大小是設計條件（§4.2）。
- **誤差方向是安全的那一邊。** 不做字距調整 = 系統性地略為高估 = 偶爾誤報，不會漏報。
- 預設 5% 的安全邊界覆蓋實測最糟的 1.43%，還有三倍餘裕。

**改判的條件**：真實專案跑出來的誤報裡，如果有可觀比例是「差 1~2% 的邊界案例」，
就回頭實作 GPOS。這條寫進 ROADMAP。

## 5. 已知限制（寫進 README）

| 限制 | 實測影響 | 處置 |
|---|---|---|
| 不做字距調整（GPOS／kern） | 最大高估 1.43%（CJK 標點） | 安全邊界吸收；只會誤報不會漏報 |
| 不做連字與複雜文字系統 | 阿拉伯文／印度系／泰文 | 標 `unmeasurable`，不猜 |
| 對應 `TextFormattingMode="Ideal"` | `Display` 模式會對齊像素格 | 偵測到就在報告標註 |
| 字型後備靠度量檔涵蓋範圍 | 缺字時標 `unmeasurable` | 大聲計數，進覆蓋率 |

## 6. 附帶發現

- **度量檔大小是設計條件。** 第一版用 `JsonSerializer` 的 `WriteIndented`，
  Segoe UI 一支字型就 **2.1 MB**（每個區間攤成五行）。改成手寫序列化、
  區間壓成一行之後是 **494 KB**。這個檔案要進使用者的 repo。
- **本機的 `python` 是 Windows 佔位捷徑**，會卡在等 stdin 而不是失敗。
  這條在 nuget skill 裡記過，又踩了一次 —— 腳本一律用 `py -3` 或改寫成別的工具。
