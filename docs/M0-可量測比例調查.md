# M0 可量測比例調查 —— 閘門判定

> 日期：2026-11-14
> 工具：`prototype/M0Survey`（拋棄式，不是正式引擎）
> **判定結果：GO**（理由見第 4 節）

---

## 1. 調查方法

規劃書第 6 節把 M0 定成 go/no-go 閘門：**寫任何正式程式碼之前，先回答「真實專案裡
有多少文字位置的可用寬度是靜態算得出來的」。**

掃描範圍：**1,921 個 XAML 檔**（解析失敗 1 個），找到 **10,858 個文字位置**，
其中 **9,149 個可在地化**（字面字串或資源字串；綁資料的 1,709 個不是翻譯對象，排除）。

語料刻意包含非作者的專案 —— 這是 XamlContrast §8.3 寫進憲法的那一條：

| 語料 | 來源 |
|---|---|
| 自家 | Cornea、Kindling、QuillNest |
| 公開 | ScreenToGif、Playnite、MaterialDesignInXamlToolkit、wpfui、ILSpy、HandyControl、MahApps.Metro、WinUI-Gallery |

### 分類定義

從文字元素往上走訪，看有沒有硬寬度上界：

| 類別 | 意思 |
|---|---|
| `Fixed` | XAML 裡直接看得到上界，路上沒有需要額外知識的東西 |
| `NeedsChrome` | 找得到上界，但路上經過樣板化控制項 —— 要「控制項預設內距表」才扣得準 |
| `NeedsGrid` | 找得到上界，但路上有 Grid 的 Auto／星號欄 —— v2 解 |
| `NeedsItems` | 找得到上界，但路上有會限制項目寬度的 ItemsControl —— v2 解 |
| `InTemplate` | 在 ControlTemplate／DataTemplate／Style 裡 —— 寬度由使用端決定 |
| `InItems` | 在 ItemsControl 裡，而且那個 ItemsControl 自己也沒有上界 |
| `Unconstrained` | 一路到根都沒有上界 —— **文字不會被裁，只會把版面撐開** |

⚠ **最後一類是「安全」，不是「不知道」。** 第一版把兩者混在一起，嚴重低估了工具的可用性。

---

## 2. 結果

### 整體

| | 全部語料 | 只看 App 畫面 |
|---|---|---|
| 可在地化文字位置 | 9,149 | 7,074 |
| **有裁切風險**（有硬上界） | 35.9% | 33.0% |
| **不會裁**（無上界） | 54.3% | 61.9% |
| **v1 算得出來 ÷ 有風險** | **75.9%** | **85.0%** |
| v1 算得出來 ÷ 全體 | 27.3% | 28.1% |
| 真正不可知（Grid／Template／Items） | 約 16% | 約 11% |

### 分類分布（全部語料）

```
Unconstrained   4,964   54.3%     ← 安全：不會被裁
NeedsChrome     1,580   17.3%     ← v1 可算（需要內距表）
Fixed             914   10.0%     ← v1 可算
NeedsGrid         710    7.8%     ← v2
InTemplate        609    6.7%     ← 不可知
InItems/NeedsItems ~370  4.0%     ← 多數不可知
```

### 各語料的差異（§8.3 的教訓：聚合會藏住差異）

| 語料 | 有風險佔比 | v1 ÷ 有風險 |
|---|---|---|
| 自家-Cornea | 91.1% | 88.2% |
| 自家-QuillNest | 82.0% | 73.6% |
| 自家-Kindling | 44.3% | 73.2% |
| 公開-MahApps | 53.5% | 77.1% |
| 公開-Playnite | 42.0% | 65.7% |
| 公開-HandyControl | 40.3% | 96.7% |
| 公開-MaterialDesign | 25.3% | 82.7% |
| 公開-WinUIGallery | 22.4% | 98.6% |
| 公開-wpfui | 22.0% | 100.0% |
| 公開-ILSpy | 25.0% | 100.0% |
| 公開-ScreenToGif | 20.0% | **34.8%** |

**自家專案的「有風險佔比」（44~91%）明顯高於公開專案（20~53%）** ——
作者習慣寫死寬度。這正是 §8.3 預測的取樣偏誤，而且這次在**調查階段**就測到了，
不是等到發版後才發現。

ScreenToGif 的 34.8% 是離群值，成因是大量使用 Grid 星號欄 —— 它是 v2 的最佳驗證對象。

### 字串層級（budget 模式的真正指標）

預算是「一個字串在所有出現位置裡的最小可用寬度」，所以該問的不是「多少位置可量測」，
而是**多少字串至少有一個可量測的位置**：

| | 全部 | App 畫面 |
|---|---|---|
| 相異字串 | 5,174 | 4,158 |
| 出現在多個位置的 | 1,407 | 1,061 |
| **至少一個位置可量測 → 給得出預算** | 29.8% | 29.4% |
| └ 全部位置都可量測 → 預算可信 | 25.1% | 25.9% |
| └ 只有部分可量測 → 預算偏鬆，要標註 | 4.7% | 3.5% |

## 3. 調查過程中修掉的四個自身缺陷

這一節存在的理由跟 XamlContrast 規劃書 §8.1 一樣：**工具自己出的錯，每一個都是
「謊報」方向。** 記下來，正式引擎不要再犯。

| # | 缺陷 | 影響 | 發現方式 |
|---|---|---|---|
| 1 | 文字位置**自己**是樣板化控制項時（`<Button Content="Save"/>`）沒標 chrome | `NeedsChrome` 從 19.1% 被低估成 **1.8%**，差十倍 | 看到數字與預期不符 |
| 2 | `Menu`／`TabControl`／`ToolBar` 被當成虛擬化清單 | 大量其實不會被裁的選單文字被丟進「不可知」 | 檢視分類定義 |
| 3 | 走到 `ItemsControl` 就中止，不往上找它自己的寬度 | 「固定寬 ListBox 裡的項目」整批進黑洞 | 同上 |
| 4 | **快顯內容（`ContextMenu`／`ToolTip`／`Popup`）被當成受視窗寬度約束** | 會給出完全錯誤的預算 | **抽樣人工核對**（QuillNest `NoteEditorWindow.xaml:838`） |
| 5 | 控制項名稱用精確比對，認不得 `MetroTabControl` 這類前綴變體 | 第三方控制項庫整組漏掉 | 抽樣人工核對（MahApps） |

**第 4、5 項只有靠人工核對才找得到**，統計數字本身完全正常。
這驗證了規劃書把「人工歸因」寫進 M0 是對的。

第 5 項與 XamlContrast 的 `Auditor.IsNonTextElement` 是**同一個教訓**
（MahApps 的 `MetroProgressBar` 對不上 `ProgressBar`）—— 同一個作者、同一個語料、
同一個坑踩第二次。這條規則要直接寫進正式引擎，不要再靠實查重新發現。

## 4. 閘門判定：GO

規劃書訂的判準是「加上內距表後 **≥ 40%** → 做；15~40% → 只做 budget；< 15% → 關掉」。

**實測 27.3%（全體）／28.1%（App 畫面），落在中間帶。**

但判準的**分母定義錯了**，而且中間帶的處方不成立：

### 4.1 分母錯在哪

判準寫的是「可用寬度靜態可知的比例」。調查之後才看清楚：
**54.3% 的位置沒有寬度上界，這是一個確定的答案，不是一個缺口。**
那些位置的文字不會被裁，它會把版面撐開——工具對它們有話可說（`reflow`），
只是說的不是「預算是多少」。

把「確定安全」算成「不可知」，等於拿一個不存在的失敗去否決專案。

### 4.2 中間帶的處方不成立

原本寫「15~40% → 只做 budget 模式，check 延後」。但這兩個模式**共用同一套寬度計算** ——
算得出寬度就兩個都能做，算不出來就兩個都不能做。把它們拆開沒有任何工程意義。
這是規劃書自己的缺陷，在此修正。

### 4.3 真正該看的三個數字

1. **有裁切風險的位置中，v1 算得出 75.9%（App 畫面 85.0%）。**
   對一個裁切檢查器來說，這才是分母。算不到的那些，多數是**根本不會裁**的。
2. ~~budget 模式的實際覆蓋是 84%。~~ **← 2026-11-14 多視角檢視後撤回，見 §4.5。**
   可信的只有 **29.8% 的數字預算**。
3. **2,494 個可量測位置**是真實的量體，不是零星幾個。

### 4.4 結論

**GO。** 但附三個必須守住的條件：

1. **README 要把覆蓋率寫在最前面**，用實測區間（各專案 v1÷有風險 34.8%~100%），
   不准只寫聚合值。
2. **每次執行都要報覆蓋率**，低於 `--min-coverage` 就 exit 3。
   工具不准在只看到三成的情況下說「沒問題」。
3. **v2 的第一順位是 Grid 求解**，不是 ItemsControl。
   Grid 佔有風險位置的 21.6%，ItemsControl 只佔 2.5% ——
   解掉 Grid 會把有風險覆蓋率從 75.9% 推到 **97.5%**。

---

### 4.5 自我檢視後撤回的一項主張（2026-11-14）

本文件第一版宣稱「budget 模式的實際覆蓋是 84%（29.8% 數字 + 54.3% 無上限）」。**撤回。**

**錯在哪**：`Unconstrained` 的真正意思是「**分析範圍內沒有宣告的**寬度上界」，
不是「不會被裁」。執行期的視窗**有**寬度——沒寫 `Width` 的 StackPanel 裡的 `TextBlock`，
文字夠長照樣會被視窗邊緣切掉。把「沒有宣告上界」當成「安全」，是拿一個沒被驗證過的
推論去撐結論。

**修正**：

- `Unconstrained` 更名為 **`NoDeclaredLimit`**，語意是「分析範圍內查不到上界」
- **它不計入覆蓋率**
- 輸出裡必須是具名值，**不准是空白儲存格** ——
  在地化負責人看到空白會當成「沒限制」然後讓譯者自由發揮

**可信的數字只有：29.8% 的字串拿得到數字預算。**
GO 的理由因此改成：**30%，而這個領域的現狀是 0%** ——
而且這 30% 恰好是設計師刻意寫死寬度的地方，也就是「這裡只能這麼寬」這個決定
最可能被翻譯打破的地方。高價值密度補償低覆蓋率。

### 4.6 驗證者實跑後發現的兩個洞（列為 M2 必要條件，非盲區）

| 洞 | 語料實測 | 後果 |
|---|---|---|
| `SizeToContent` 會讓視窗的 `Width` 失效 | **79 個檔案用了，其中 46 個同時寫了數字 `Width`** | 會給出**完全錯誤的預算** |
| 水平捲動的 `ScrollViewer` 讓上界失效（文字可捲動，不會被裁） | **60 處** | 同上 |

兩者的失敗方向都是**產生錯誤數字**而不是漏報。對一支要把數字餵給譯者的工具來說，
這是最糟的失敗模式，所以它們是 M2 的**必要條件**，不是「已知限制」。
